# 3.2 Search Engine: TF-IDF Cosine and BM25

We implement a review-level inverted index and two ranking functions from scratch: TF-IDF with cosine similarity and Okapi BM25. A shared tokenizer is applied at index and query time, while SQLite provides persistence rather than ranking. On a reproducible sample of 50,000 Yelp reviews, six diverse queries produce different first-ranked documents under the two models and Top-10 overlaps of two to six documents. Qualitative inspection explains both useful ranking changes and failures involving partial attribute matches, word senses and negation. Controlled changes to BM25's length normalization substantially alter the selected reviews. These findings describe the recorded sample and query set; ranking agreement and lexical coverage do not establish relevance accuracy.

## 3.2.1 Search Architecture and Indexing

Group B implements the search component in Assignment §3.3: an inverted index, persistent storage, TF-IDF cosine scoring, BM25 scoring, and comparison on diverse queries. The system retrieves individual reviews rather than aggregated businesses. Its public Python interface is `yelptext.interface.search_engine`; a common command-line interface supports index construction, single queries and query batches.

### Shared preprocessing and document boundaries

The data and corpus component supplies a prepared-review reader and a shared tokenizer pipeline. The default builder reads each review's stable `doc_id` and original `text`, calls `pipeline.terms(text)`, and uses the returned occurrences to build postings. The same pipeline processes query strings. The experiment lowercases text, preserves contractions and emojis, and splits hyphenated words. It filters punctuation, retains stopwords such as *and*, *the* and *not*, and disables part-of-speech filtering. NLTK supplies the shared pipeline's stopword resource [5](https://www.nltk.org/); the custom tokenizer itself is supplied by Group A rather than reimplemented by Group B. Each persisted index records a tokenizer fingerprint; loading and querying reject an incompatible pipeline.

Each posting stores a term, an internal integer `docno` and its within-document frequency. The document table maps `docno` to the stable external `doc_id`; search results retain the external ID. The SQLite database stores review text and business metadata for display, document lengths and TF-IDF norms, term document frequencies and IDFs, and versioned index metadata. Business names, categories and ratings do not affect the score. SQLite [9](https://sqlite.org/docs.html) handles storage; no third-party ranking module computes the scores.

### Index-local statistics and persistence

Let $f_{t,d}$ denote the count of term $t$ in the filtered representation of review $d$, $df_t$ the number of indexed documents containing $t$, and $N$ the number of indexed reviews. We compute these statistics from the actual index collection, rather than reusing a full-corpus vocabulary's DF after filtering. The indexer accumulates global document length during its scan:

$$
|d|=\sum_t f_{t,d},\qquad
 \operatorname{avgdl}=\frac{\sum_{d\in D}|d|}{N}.
\tag{1}
$$

A valid review with no retained terms still contributes to $N$ with length zero. For an empty collection, the implementation sets $\operatorname{avgdl}=0$ and returns no matches. Listing 1 shows the central counting and batch buffering; serialization, validation and the database flush routine are omitted.

**Listing 1. Current `build_index` excerpt. Buffered postings use integer `docno`; global counters determine Equation 1.**

```python
counts = Counter(_terms(tokenizer, review["text"]))
length = sum(counts.values())
docno = document_count
document_rows.append((docno, review["doc_id"], serialized, length))
posting_rows.extend(
    (term, docno, tf) for term, tf in sorted(counts.items())
)
document_count += 1
total_terms += length
if document_count % _BATCH_SIZE == 0:
    flush_batch()
```

Batches are flushed every 1,000 documents and once after scanning. The indexer then builds the SQL indexes and derives DF, IDF and complete document-vector norms. It builds a temporary database and publishes it only after successful completion. Duplicate IDs are errors, existing indexes are not overwritten, and loaded indexes are read-only. The current SQLite format is version 2; version-1 indexes require rebuilding. An optional MapReduce builder supports two to eight workers; the sample experiment uses the default single worker. A separate compact backend uses NumPy arrays [1](https://doi.org/10.1038/s41586-020-2649-2) and packed postings; the required experiment below uses the default SQLite backend.

## 3.2.2 Ranking Implementations

Both scoring functions are implemented with explicit arithmetic in `ranking.py`. Their variants and edge cases are stated here because reasonable TF and IDF conventions can otherwise produce different rankings. All logarithms are natural.

### TF-IDF with cosine similarity

Following the vector-space model [3](https://nlp.stanford.edu/IR-book/), the implementation uses smoothed IDF and logarithmic term frequency:

$$
\begin{aligned}
\operatorname{idf}_T(t)&=\ln\frac{N+1}{df_t+1}+1,\\
 w(t,x)&=(1+\ln f_{t,x})\operatorname{idf}_T(t)\quad(f_{t,x}>0),\\
 s_T(q,d)&=\frac{\sum_{t\in q\cap d}w(t,q)w(t,d)}
 {\lVert\mathbf{w}_q\rVert_2\lVert\mathbf{w}_d\rVert_2}.
\end{aligned}
$$

The document norm includes *all* indexed terms in the document, including terms absent from the query. Query weights use the same index-local IDF. Out-of-vocabulary (OOV) query terms are removed before computing its norm. This policy makes an unknown term unable to dilute the weights of known terms.

### Okapi BM25

The implementation uses a positive-IDF BM25 variant [8](https://doi.org/10.1561/1500000019):

$$
\begin{aligned}
\operatorname{idf}_B(t)&=\ln\left(1+\frac{N-df_t+0.5}{df_t+0.5}\right),\\
 s_B(q,d)&=\sum_{t\in q\cap d}
 f_{t,q}\operatorname{idf}_B(t)
 \frac{f_{t,d}(k_1+1)}
 {f_{t,d}+k_1(1-b+b|d|/\operatorname{avgdl})}.
\end{aligned}
$$

The baseline is $k_1=1.5$, $b=0.75$. Here $k_1$ controls term-frequency saturation and $b$ controls length normalization. Repeated query terms contribute linearly through $f_{t,q}$; we do not add a query-frequency saturation parameter. The code validates finite parameter values with $k_1>0$ and $0\leq b\leq1$. Average length comes from indexing, not the current query's matching documents. Listing 2 shows the scoring loop, including an algebraically equivalent calculation that avoids large intermediate products when $k_1\geq1$. For TF-IDF, division by the query norm follows the shown accumulation; the excerpt alone is not the complete cosine calculation.

**Listing 2. Scoring excerpt from `search`. The terms' IDFs and query weights are computed immediately before this loop.**

```python
for doc_id, tf, document_length, document_norm in postings:
    if ranker == "tfidf":
        document_weight = (1.0 + math.log(tf)) * tfidf_idf
        scores[doc_id] += document_weight * query_weight / document_norm
    else:
        length_normalization = 1.0 - b + b * document_length / average_length
        # Dividing numerator and denominator by k1 for large values
        # avoids overflowing intermediate products for finite inputs.
        if k1 >= 1:
            tf_weight = tf * (1.0 + 1.0 / k1) / (tf / k1 + length_normalization)
        else:
            tf_weight = tf * (k1 + 1.0) / (tf + k1 * length_normalization)
        scores[doc_id] += bm25_idf * tf_weight * query_tf
```

### Candidate selection and ordering

Candidates are the union of postings for known query terms, giving OR matching. The engine sorts by descending score and then ascending `doc_id` to resolve ties deterministically. Under the reported filtering policy, empty, punctuation-only and all-OOV queries return no matches; unmatched documents are not added merely to fill Top-$K$. The index does not store token positions or offsets, so it provides no phrase, proximity or highlight semantics. Numeric scores from the two models have different scales and are not compared directly.

## 3.2.3 Experimental Design

The recorded experiment uses Yelp review and business data [11](https://business.yelp.com/data/resources/open-dataset/). Its sampling record reports a scan of 6,990,280 reviews, stable bottom-$k$ selection of 50,000 reviews using seed 42 and FNV-1a priorities, and a join against 150,346 business records. This deterministic hash sample is not assumed representative or statistically uniform. Its review dates span 19 April 2005 to 19 January 2022. The ranking tables and qualitative observations below are retained from this recorded experiment and also documented in the integrated project's search report. Table 1 summarizes the collection after punctuation filtering and the updated index footprint reported by that integration record; the footprint was not independently remeasured.

| Measure                       | Value      |
| ----------------------------- | ---------- |

The fixed queries under `[analysis.search].queries` in `configs/sample.toml` are Q1 *good service*, Q2 *cheap Italian restaurant*, Q3 *family friendly atmosphere*, Q4 *slow delivery*, Q5 *best coffee and breakfast*, and Q6 *not worth the price*. They cover service, price and cuisine, ambience, delivery, meal preferences and negated value judgments. Both models use the same documents, tokenizer, query strings and $K=10$; every query term is known to this index. The sample contains 33,972 reviews in the Restaurants category and 6,139 in Breakfast & Brunch, with overlapping categories. The queries are exploratory information needs, not a representative benchmark or relevance labels.

We measure Top-10 set overlap, Jaccard agreement, mean returned-document length, and the fraction of returned documents containing all distinct query terms. This last measure is *lexical coverage*, not precision: a document can contain all words while failing the requested meaning. In the current workflow, `scripts/run_search_experiment.py` generates a manifest, full rankings and diagnostic tables. Notebook 04 is presentation-only: it reads these artifacts and displays selected results. The supplied notebook has no saved outputs, and generated search artifacts are excluded from the source distribution; the commands in Appendix A regenerate them.

## 3.2.4 Results and Discussion

### Ranking differences across six queries

Table 2 shows that all six first-ranked documents differ between the models. Top-10 overlap ranges from two documents for Q5 to six for Q3. BM25 returns longer reviews on average and higher all-term coverage for every query in this sample. These patterns describe weighting and selection; they do not alone identify which model is more relevant.

**Table 2. TF-IDF and BM25 on the same six queries.** $O@10$ is the number of common Top-10 document IDs. $C@10$ is all-query-term lexical coverage, not a relevance metric. All queries returned ten results under each model.

| Query | Query text                 | $O@10$ | TF-IDF mean length (tokens) | BM25 mean length (tokens) | TF-IDF $C@10$ | BM25 $C@10$ |
| ----- | -------------------------- | ------ | --------------------------- | ------------------------- | ------------- | ----------- |
| Q1    | good service               | 3      | 14.8                        | 20.6                      | 0.90          | 1.00        |
| Q2    | cheap Italian restaurant   | 3      | 25.7                        | 77.8                      | 0.10          | 0.40        |
| Q3    | family friendly atmosphere | 6      | 23.5                        | 31.6                      | 0.60          | 1.00        |
| Q4    | slow delivery              | 4      | 22.8                        | 65.7                      | 0.10          | 0.60        |
| Q5    | best coffee and breakfast  | 2      | 24.0                        | 62.9                      | 0.10          | 0.80        |
| Q6    | not worth the price        | 4      | 19.1                        | 34.0                      | 0.40          | 1.00        |

#### Useful results can differ without indicating failure.

For Q1, TF-IDF first retrieves a concise First Watch review praising breakfast food and service (eight tokens). BM25 first retrieves a 30-token Asian-market review that repeatedly praises service, freshness and prices. Both support the information need despite their different domains and lengths. Similarly, Q3's first TF-IDF review explicitly describes children enjoying the venue, while BM25's first review praises family friendliness and atmosphere. These examples prevent interpreting every ranking disagreement as an error.

#### OR matching can lose required attributes.

For Q2, TF-IDF's top result discusses a Mexican restaurant and matches *cheap* without satisfying the Italian requirement. BM25's first result describes an inexpensive meal at an Italian chain. However, BM25 also retrieves a *cheap tasting* quality complaint and a review saying a sandwich is *not cheap*. Term presence does not enforce affordability or the conjunction of all requested attributes. Q3 has a related issue: TF-IDF's third result mentions friendly staff and atmosphere without discussing families.

#### Word senses and negation remain unresolved.

For Q4, the first two TF-IDF reviews praise fast delivery and contain no *slow*. BM25's leading result contains both query terms but reports hearsay; its second concerns the pace of dishes arriving during a restaurant meal. Thus improved coverage still permits a delivery-sense mismatch. For Q6, TF-IDF's first review praises price and value without *not*; BM25's first contains an explicit negative value judgment. Both models rank a directly relevant criticism second. These cases illustrate successful lexical matches and errors, not general semantic understanding of negation.

#### Coverage can also understate useful content.

For Q5, TF-IDF's first result praises breakfast while criticizing the coffee; BM25's first positively endorses both. The BM25 review lacks the literal word *and*, although it expresses the intended conjunction. Consequently, requiring all query terms is itself an imperfect diagnostic when stopwords remain. A higher coverage fraction cannot be relabeled precision or used to prove that BM25 is universally better.

### BM25 parameter sensitivity

We vary one parameter at a time around $(k_1,b)=(1.5,0.75)$: $b\in\{0,0.75,1\}$ at $k_1=1.5$, and $k_1\in\{0.5,1.5,2\}$ at $b=0.75$. Table 3 reports agreement with the baseline, not relevance quality. With $k_1=1.5$, setting $b=0$ removes length normalization. The mean result lengths increase from the baseline 20.6, 77.8, 31.6, 65.7, 62.9 and 34.0 tokens to 479.9, 291.5, 218.1, 351.3, 391.5 and 238.8, respectively. Only 0, 3, 3, 2, 1 and 1 baseline documents remain in the corresponding Top-10 sets. This controlled change demonstrates that global length normalization materially affects document selection. Longer reviews are not inherently worse; relevance still requires judgment.

**Table 3. BM25 Top-10 Jaccard agreement with the baseline $(k_1,b)=(1.5,0.75)$.** Q1–Q6 follow Table 2. Higher values mean greater ranking agreement, not greater relevance. Values match the TeX heatmap, rounded to two decimal places.

| ----- | ------------ | --------- | --------- | ------------ | ---------- |
| Q1    | 1.00         | 0.00      | 0.18      | 0.82         | 1.00       |
| Q2    | 1.00         | 0.18      | 0.43      | 0.54         | 0.54       |
| Q3    | 1.00         | 0.18      | 0.82      | 1.00         | 1.00       |
| Q4    | 1.00         | 0.11      | 0.54      | 0.67         | 0.54       |

At $b=0.75$, varying $k_1$ from 0.5 to 2 preserves each query's first-ranked document in this run, although some lower ranks and Top-10 members change. This supports a sample-specific statement about sensitivity, not an optimal parameter choice. Choosing parameters for relevance would require judged development queries and a separate evaluation set.

## 3.2.5 Validation and Limitations

The integrated suite passes 118 tests under CPython 3.12.4, including 102 search-specific tests. Tests independently check hand-counted postings and TF-IDF/BM25 scores, complete document norms, repeated and OOV terms, ties, empty inputs, failed build cleanup, persistence, fingerprint mismatch and CLI outputs. The compact backend is also compared against SQLite. A tiny real-interface smoke run checks shared-reader/tokenizer integration. These checks establish arithmetic and integration behavior; they do not replace relevance evaluation.

The analysis is limited to 50,000 reviews and six exploratory queries. OR matching, absent phrase positions, no stemming or synonym expansion, and no negation-scope model explain several observed errors. No consistently judged relevance set was constructed, so we report no Precision, Recall, MAP or nDCG. No full-corpus performance conclusion follows from this sample. The current sample configuration uses one untimed warm-up followed by one timed call for each query and ranker. Such warm timings are environment-specific; historical build and query timings are not benchmarks of the current checkout. A next evaluation should pool both models' results, judge complete information needs consistently, and separate parameter selection from final testing.
